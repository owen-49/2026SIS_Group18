二 · 审计耗时（结构档）

真实 uvicorn + HTTP 边界 · provider 是 pin 的，每次请求固定睡 0.05 s

实测中位数（5 次重复） 参照：请求数 × 0.050 s

这条曲线要证明的不是"有多快"，而是"怎么变慢"：一个文档的成本是它的 provider 请求数乘以单次延迟，请求是串行发出的。曲线与参照线平行，斜率就是证据。

百分位用 nearest-rank（第 ⌈p×n⌉ 个观测值，不插值），所以 5 次重复的中位数 是第三个观测值。机上噪声小于 2%。

差分消掉固定开销，不做拟合。四个区间的每请求成本落在 0.0544–0.0551 s， 没有随 N 上升或下降：并发实现会让曲线在 N 增大时变平，这里没有。

这不是产品的延迟。 档位说明：real uvicorn on 127.0.0.1, in-process pins: the HTTP boundary is inside the measurement and the network is not。 pin 不打开 socket，所以这些秒数度量的是应用自己的串行链，不是网络。真实档的冷/热延迟要连 真实 provider，同样受当日额度限制。延迟没有及格线，本页只报基线数字。

四 · 复现

全部离线、确定性、无 key

cd claimtrace

# 审计准确率：受控重放。缺 pin 的用例不会被猜分，只会被列出来
python3 backend/scripts/audit_benchmark.py --mode replay \
    --cases backend/tests/benchmarks/audit_cases.json

# 审计计时：结构 N 曲线（默认 N=5,10,20,40,80／各 5 次／每次请求 0.05 s）
python3 backend/scripts/audit_benchmark.py --mode timing --report audit_timing.json

# 核验：零成本预算测算，以及离线打分
python3 backend/scripts/verify_benchmark.py --estimate \
    --pairs engine/tests/benchmarks/claim_passages.worksheet.json
python3 backend/scripts/verify_benchmark.py --mode replay --check

本页审计数字来自 audit_benchmark.run() 对"请求全部有 pin 的那 34 条"打分；补齐剩余 8 条 pin 之后，上面第一条命令会一次性 覆盖全部 42 条，并复现同一组数字。挑出这个子集的探针是本机的一次性脚本、没有入库， 它只是把缺 pin 的用例摘出去；补齐 pin 之后就不再需要它。

原始数据：docs/accuracy-baseline/audit_accuracy_subset.json（34 条评分）、 docs/accuracy-baseline/audit_timing.json（N 曲线）· 与页面同目录。 口径：状态标签与安全不变量读自 docs/audit-contract.md； 时间用 time.perf_counter() 紧贴 HTTP 调用；百分位为 nearest-rank，不插值。 本页是尚未提交的草稿，被测的脚本已经并入 main。核验准确率、真实档冷/热耗时都还没有数字，本页不替它们说话。
