# User Personas

> 综合 W1–W3 用户研究整理（目标：访谈 5 位近期向顶级会议投稿的博士生/研究员）。  
> 三个人物画像覆盖 ClaimTrace 的三类核心用户，用于驱动 user story 的优先级排序。

---

## P1 — 焦虑的第一作者：Xiaowei（博士生）

| 维度 | 描述 |
|------|------|
| **背景** | CS 博三，正在写一篇准备投 NeurIPS/ICML 的一作论文，负责整合三位合著者写的 Related Work 和 Discussion |
| **目标** | 在截稿前把所有引用都核查一遍，避免因为引用错误被 Reviewer 打回 |
| **痛点** | ① 合著者写的引用他不敢全信，但又没时间逐篇下载 PDF 核对；② 从 Overleaf 切到 Zotero 再到 PDF 阅读器来回跳，思维被打断；③ 有一次审稿人在 rebuttal 里指出"你引的这篇结论其实相反"，当场社死 |
| **典型场景** | 截稿前 48 小时，发现 Related Work 里 30+ 个引用都没验证过，逐篇 Ctrl+F 要花几个小时，只能凭感觉放过大多数 |
| **对 ClaimTrace 的期望** | "在 Overleaf 里 hover 一下就知道这个引用对不对，不用离开编辑器；能批量把整篇论文过一遍，告诉我哪 3 个引用最该人工复核" |
| **付费意愿** | 作为学生工具免费最好，但团队订阅可接受 |

## P2 — 把关的导师：Dr. Chen（PI / 导师）

| 维度 | 描述 |
|------|------|
| **背景** | 副教授，带 5 个博士生，学生交来的论文草稿他都要做质量把关，但时间碎片化 |
| **目标** | 快速抽查学生论文里的引用是否诚实、准确，不用逐篇读原文 |
| **痛点** | ① 学生论文里的引用质量参差不齐，他没法一篇篇验证；② 学生有时图省事从 ChatGPT 复制引用，导师很难察觉；③ 他希望看到"证据"而不是"结论"，才能给学生具体的修改意见 |
| **典型场景** | 学生发来 8 页草稿，他有 30 分钟给出反馈。想快速定位"哪些引用的原文支持力度存疑"，然后针对性地让学生去改 |
| **对 ClaimTrace 的期望** | "给我一个风险排序的报告，红色标出最可疑的引用，附上原文证据，我好直接截图发给学生" |
| **付费意愿** | 实验室/院系订阅可接受，愿意为节省时间付费 |

## P3 — 挑剔的审稿人：Reviewer 2（会议审稿人）

| 维度 | 描述 |
|------|------|
| **背景** | 每年审 5–10 篇顶会投稿，熟悉领域文献，对"引用注水"和"错误引用"很敏感 |
| **目标** | 快速核查投稿核心主张的引用是否准确，作为 accept/reject 的论据 |
| **痛点** | ① 直觉觉得某处引用"不对劲"，但要花时间找原文验证，审稿时间有限；② 需要在 review 里给出"具体、可引用"的证据，而不是泛泛说"引用不严谨" |
| **典型场景** | 读到某句 claim 引用了某篇他熟悉的论文，凭记忆感觉作者过度解读了，想核实原文，但没有一个快速的工具 |
| **对 ClaimTrace 的期望** | "把 claim 和它引的原文并排给我看，我 30 秒就能判断作者有没有曲解" |
| **付费意愿** | 个人不付费，但这是"评审工具"而非"写作工具"的场景，可作为未来 B2B 方向 |

---

## 画像要点总结

| Persona | 核心诉求 | 使用场景 | 对应功能 |
|---------|----------|----------|----------|
| P1 博士生 | 快、不打断写作流、批量 | 交稿前审计 | hover 验证 + 批量审计 |
| P2 导师 | 风险排序 + 证据 | 抽查学生草稿 | 审计报告 + 原文证据 |
| P3 审稿人 | 并排对照 claim vs 原文 | rebuttal/评审 | 语义对齐 + 证据展示 |

**共性洞察**：所有画像都强调「**要看到原文证据，而不是只要 AI 结论**」——这直接支撑了 ClaimTrace「展示匹配段落 + 判定」而非「只给标签」的设计原则。
